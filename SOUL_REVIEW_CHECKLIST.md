# SOUL_REVIEW_CHECKLIST.md

Use this checklist before building, reviewing, or accepting any product or code change.

The goal is not to make code look sophisticated. The goal is to preserve buyer value, evidence, human control, and cashflow.

Human nature is the invariant behavioral dataset. Sandbox scenarios are valid when they model stable human behavior honestly.

Read `HUMAN_NATURE_AXIOMS.md` before reviewing product proposals or workflow code.

## 1. Implementation Integrity Check

Every feature or workflow must answer:

1. Buyer pain:
2. Payer:
3. Payment trigger:
4. AI/operator action:
5. Evidence produced:
6. Human approval boundary:
7. Risk reduced:
8. Acceptance criteria:
9. What should not be built yet:

If any item is unclear, choose the smallest manual-first implementation that can produce evidence and paid proof.

## 2. Six-Part Workflow Contract

Every important workflow should have:

1. Goal - what the user wants to achieve.
2. Loss - what the user avoids losing.
3. AI work - what labor AI performs.
4. Evidence - what proof is stored.
5. Human approval - what commitment human approves.
6. Paid unit - what delivered-work unit can be charged.

If one part is missing, the workflow is not mature enough.

## 3. Soul Review Questions

Reviewers must ask:

- Does this reduce a real buyer loss?
- Does the scenario model a stable human driver: wanting gain, fearing loss, confusion, pride/status, doubt, distrust, urgency, or desire for control?
- Does it create evidence, not only UI state?
- Does it keep human approval at money, legal, reputation, or irreversible boundaries?
- Does AI perform real work or only produce text?
- Does it avoid generic CRM, ERP, marketplace, chatbot, or dashboard drift?
- Does it preserve manual-first workflow truth?
- Does it survive platform API failure through manual or alternate-source fallback?
- Does it make the user stronger, clearer, and more in control?
- Does it avoid fake urgency, hidden persuasion, and emotional pressure?
- Does it connect to paid proof or delivered-work billing?

## 4. Red Flags

Defer or reject if the change is mostly:

- dashboard appearance;
- generic CRUD;
- chatbot output without evidence;
- marketplace complexity before paid proof;
- automation before manual workflow truth;
- AI autonomy without approval boundary;
- recommendation without risk and uncertainty disclosure;
- platform dependency with no fallback;
- feature imagination without buyer loss.
- rejecting obvious human-risk design only because production data is not yet available;
- using sandbox data to claim exact market facts without evidence.

## 5. Required Recommendation Shape

High-impact AI recommendations should include:

- recommendation;
- why;
- evidence;
- risks;
- alternatives;
- uncertainty or missing proof;
- human decision needed;
- next action after approval.

No evidence, no confident recommendation.

Human-nature priors can justify risk scenarios. Evidence is still required for specific factual claims.

## 6. Final Acceptance Rule

Accept the change only if it leaves the user:

- clearer;
- better informed;
- more capable;
- less exposed to avoidable loss;
- closer to a real economic decision;
- still in control of commitment.

If the user becomes weaker or more dependent, the feature is wrong.
